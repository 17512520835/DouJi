# 05 · 架构契约

> **V7.1.1 Engine Core Phase 4 封箱版的关键架构决策摘要。**
>
> 完整版见 `docs/iteration-archive/V7.1.1_EngineCore_Phase4_架构契约.md`。本节只讲"为什么这么定"以及"这些约束对 PM 工作的影响"。

## 1. 总览：三层架构

```
┌─────────────────────────────────────────────┐
│  UI 层（前端）                                │
│  - online.html / 7.7MB 单文件版              │
│  - 只能通过 Observation 获取状态                │
│  - 不能直接持有 GameState                       │
└──────────────────┬──────────────────────────┘
                   │ dispatch(command)
                   │ getObservationForSide(side)
                   ▼
┌─────────────────────────────────────────────┐
│  Engine Core（生产引擎）                       │
│  - engine.v721.core.bundle.js                │
│  - 只暴露 window.GameEngine Facade            │
│  - 真实 GameState 在模块私有 WeakMap 中        │
│  - 隐藏信息只能通过 Observation 出口             │
└─────────────────────────────────────────────┘

测试需要内部接口时用：
┌─────────────────────────────────────────────┐
│  Debug Build（仅测试）                        │
│  - engine.v721.core.debug.bundle.js          │
│  - 不被任何 HTML 引用                          │
│  - 提供细粒度规则函数                          │
└─────────────────────────────────────────────┘
```

## 2. 关键架构决策

### 决策 1：生产 / Debug 双 build

**问题：** 测试需要访问内部规则函数，但生产代码暴露内部接口会破坏封装。

**决策：** 物理分离为两个 build 文件。生产 build 只暴露 `window.GameEngine` Facade；debug build 暴露内部函数但不被 HTML 引用。

**PM 影响：**
- 测试代码无论如何无法影响生产路径
- Phase 6 跨版本比对时，可以单独验证"生产 API 是否稳定"

### 决策 2：UI 不能直接持有 GameState

**问题：** 如果 UI 直接读 `gameState.players[0].hand`，会出现"前端缓存 vs 真实状态"不一致。

**决策：** UI 只能调 `getObservationForSide(side)`，引擎返回受控快照。

**PM 影响：**
- 隐藏信息隔离是自动的（Observation 里只有己方手牌 + 对手数量 / hidden 占位）
- 联机版的"客户端只看本方信息"是天然的——服务端只下发本方 Observation

### 决策 3：Expansion History 只有一个权威账本

**问题：** 旧代码里有多处展开历史镜像，导致"哪些是事实"出现分歧。

**决策：** `ExpansionLedger` 作为唯一事实源。command-local event sink 是模块私有临时收集器，不存入 GameState，因此不形成第二套历史账本。

**PM 影响：**
- 回放（Replay）能 100% 重现对局，因为只有一套历史
- Phase 6 跨版本比对才能成立——不同版本对"同一动作序列"必须产生同一 Digest

### 决策 4：Forbidden Mirror 验证器两层防护

**问题：** 旧验证用"源码字符串里出现 forbidden 即失败"，导致正常的 invariant 检查代码也被误判。

**决策：** 两层防护：
1. 运行态 `assertCoreInvariants()`：任何 forbidden key 回到 `mechanics` 立即报错
2. 静态语义扫描：允许字段名存在于 invariant 禁止名单 / 测试中，但禁止 `mechanics.xxx`、`mechanics['xxx']`、对象业务字段 `xxx:` 等实际业务上下文

**PM 影响：**
- 验证规则不会"误伤"自己
- 旧 forbidden mirror 回归（如拉封骑士 / 骑枪总冲的 CHASE_WINDOW 提前进入）能被 fuzz 抓到

## 3. Phase 4 封箱的 6 条停止条件

任何后续引擎修改都必须保证这 6 条仍成立：

1. **Production UI cannot mutate rules except through Core commands** — UI 不能绕开 Core 改规则
2. **Hidden information only exits through Observation** — 隐藏信息只能从 Observation 出口
3. **Expansion history has one authoritative Ledger** — 展开历史只有一个权威账本
4. **Replay(config + seed + commands) reproduces digest** — 回放能 100% 重现
5. **Random legal sequences preserve invariants** — 随机合法序列保持不变量
6. **Golden Masters remain preserved** — Golden Master 不被破坏

## 4. 联机版的架构继承

Online Phase 1 直接继承了 Phase 4 的架构：

| Phase 4 决策 | Online 版的对应做法 |
|-------------|-----------------|
| UI 只能通过 Observation 获取状态 | 客户端只接收本方 Observation，对手手牌数量 / hidden 占位 |
| Replay(config + seed + commands) reproduces digest | 联机服务器持有服务端真实状态，断线重连可凭 resume token 恢复 |
| Expansion history has one authoritative Ledger | 服务端 Core Event Ledger 决定通报内容，客户端不能伪造 |
| Hidden information only exits through Observation | 隐藏信息（手牌 / 牌堆）服务端持有，永远不下发到对手客户端 |

**PM 价值：** Online Phase 1 不需要重新设计安全边界——Phase 4 已经把约束写死在 Core 里。

## 5. 后续引擎修改的流程

按 Phase 4 封箱声明：

> 后续引擎修改按正常 bugfix / feature 流程处理，不再继续 Phase 5 / Phase 6 式架构迁移。

V7.2.1 之后的版本确实都是按这个原则处理——每个修复都先验证 6 条停止条件仍成立，再继续。V7.2.7 Phase 6 跨版本比对就是"对 6 条停止条件的最终审计"。

## 6. 给工程师 / 面试官的 30 秒讲解

> "这个游戏的引擎层是确定性纯函数模块。UI 通过 dispatch(command) 提交动作，通过 getObservation(side) 读快照。手牌等隐藏信息只在 Observation 里对所属 side 暴露。Replay 用 (config + seed + commands) 100% 重现 Digest。Phase 4 把这些约束写进了 6 条停止条件，V7.2.7 Phase 6 用跨版本比对证明这些约束在 v714 → v721 升级中没破。联机版直接继承这套边界——服务端 Core 持有真实状态，下发 Observation 给各自客户端。"
