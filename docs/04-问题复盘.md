# 04 · 问题复盘

> **这个项目里我踩过的坑、做错的决策、没有按 PM 原则执行的时刻。**
>
> 写复盘不是检讨，是给未来的自己（以及面试官）一份诚实的过程记录。

## 1. 我犯过的三个最严重的错

### 错 1：低估了 Engine Core 化的迁移工作量

**当时的想法：** "把核心逻辑抽出来，UI 改成调用 Core——大概 2 周能做完。"

**实际情况：** 跨 4 个 Phase、10+ 周，最后还多了一轮 Phase 6 Golden Master 跨版本比对才算真正封箱。

**根因：**
- 老 HTML 里耦合了 UI 与规则，迁移时不断发现"这个 UI 隐含依赖了这个规则的边界条件"
- 没有先冻结老代码，导致老代码边迁边改，回滚成本高
- Phase 1–3 每阶段都"觉得差不多了"就往前推，结果 Phase 4 必须做 fuzz 才发现一个封箱 bug（拉封骑士 / 骑枪总冲的 CHASE_WINDOW 提前进入问题）

**我现在会怎么做：**
1. 第一阶段先做"老代码冻结 + 新代码平行开发 + 跨版本 harness 对比"，**不直接动老代码**
2. 每个 Phase 封箱前必须满足"上一 Phase 的所有承诺仍成立"，否则不能进下一 Phase
3. Fuzz 测试要**早于**封箱引入，而不是封箱前一周才补

### 错 2：V7.2.6 把"环境阻断"和"代码问题"混淆

**当时的想法：** "长局 12/12 PASS 了，浏览器跑不了是环境问题，不影响发布。"

**实际问题：** 我把环境阻断写进了 PASS 报告的备注里，**没有单独标记为 PENDING**——这给读者一种"全绿通过"的错觉。

**后来怎么修：** V7.2.7 Phase 6 重新检查时，把 `Browser URL Entry Runtime` 单独标为 `PENDING_ENVIRONMENT_GATE`，并明确"这不是代码 FAIL，是最终发布流程中唯一仍需在正常浏览器环境执行的人工门禁"。

**我现在会怎么做：**
- PASS / FAIL / PENDING 三态必须**物理隔离**——不同颜色、不同字段、不同结论分支
- PENDING 的原因必须可复现，不能含糊带过
- 不能因为"反正别人跑也会遇到"就不标记

### 错 3：V7.2.10 借联机版"夹带"了囚徒回血修正

**当时的想法：** "反正这一版在修联机，顺便把囚徒回血数值改一下，省一个版本。"

**实际后果：**
- 评审 V7.2.10 时要同时看 3 类变更（联机框架 / 战斗通报 UI / 数值），心智负担大
- 回滚难度高——如果联机框架要回退但囚徒回血要保留，必须手动 cherry-pick
- 验证脚本要重写——没法复用 V7.2.9 的全套

**我现在会怎么做：**
- "顺带修"必须在迭代说明里**显式列出**，并独立小节写影响面
- 大版本尽量单一主题；如果确实要"顺带修"，把它们拆成两个 commit 而不是混在一起

## 2. 我做的最对的三个决策

### 对 1：把 Engine Core 拆成生产 + Debug 双 build

**背景：** Engine Core 化的时候，需要在生产代码里暴露测试用接口。

**决策：** 不暴露。生产 build（`engine.v714.core.bundle.js`）只暴露 `window.GameEngine` Facade；测试需要的内部接口放到 debug build（`engine.v714.core.debug.bundle.js`），debug build 不被任何 HTML 引用。

**结果：** 测试代码无论如何都无法影响生产路径——这是 Engine Core 封箱能成功的关键。

### 对 2：Phase 6 跨版本 Golden Master 比对

**背景：** Phase 4 封箱后，担心 v714 → v721 升级过程中有未知回归。

**决策：** 不只跑 v721 单版本回归，而是固定 Seed 跨 v714 / v721 比对玩家可观察 Digest。

**结果：** 发现 4 处已批准差异（V7.2.4 + 法尤姆 PendingChoice 修复），0 处无法解释差异。如果不做这个比对，这些差异不会被任何回归脚本发现。

### 对 3：Online Phase 1 选权威服务器而不是锁步模拟

**背景：** 联机有两条技术路线：锁步模拟（双方各自跑 Core、同步动作序列）vs 权威服务器（服务器跑 Core、客户端只发动作）。

**决策：** 选权威服务器。

**理由：**
1. 隐藏信息（手牌 / 牌堆）必须服务端持有，不能下放客户端
2. Core 已经 386KB，前端加载 + 首次同步会很慢
3. 权威服务器调试更容易（不用两台浏览器复现）
4. 联机服务器代码量很小（`online-server.js` 约 200 行），不需要服务端框架

**代价：** 服务器需要常驻，部署门槛比锁步模拟高。但这个代价换来了"防作弊 + 易调试 + 隐藏信息隔离"三项收益。

## 3. 我现在仍不满意的几个地方

### 3.1 没有"用户访谈"过程

整个 12 个版本的需求来源都是**我自己测试对局 + 几个朋友小范围反馈**。没有做过正式的用户访谈。

**影响：** 一些 P1 体验问题可能是"只有我会遇到"，不一定代表真实用户痛点。

**改进方向：** 下一项目先做 3–5 个目标用户的访谈，定量 + 定性结合，再进设计阶段。

### 3.2 阶段门禁规则没写成可执行脚本

V7.2.6 的"12/12 PASS"是人工跑 + 人工看 JSON 报告。如果版本再多两个，这一过程会变成人力瓶颈。

**改进方向：** 写一个 `gate_check.js`，自动跑全套回归并按 PASS / FAIL / PENDING 分类输出结论。任何"全绿"必须有这个脚本的输出来背书。

### 3.3 AI 编码辅助的边界没有早期定义

我从 V7.1.1 开始用 AI 辅助编码，但**没有一开始就明确边界**——哪些让 AI 写、哪些必须自己写。

**结果：** 早期几个版本的引擎实现细节，部分我自己都讲不清楚"为什么这么写"——因为那是 AI 生成的。这削弱了面试时对作品的掌控感。

**改进方向：** 本作品集用 `docs/06-AI辅助边界声明.md` 做了事后澄清；下一项目从 Day 1 就定义 AI 边界。

## 4. 给面试官的问题与我的回答

**问：** "你为什么没在 V7.2.6 之前就发现 Browser URL Entry Runtime 的环境阻断问题？"

**答：** 发现得早，但当时归类为"环境问题"，没有升级为独立 PENDING。V7.2.7 重新分类。教训：PENDING 必须独立成态，不能"挂靠"在 PASS 上。

**问：** "如果你重做这个项目，你会先做什么？"

**答：**
1. 先冻结老代码，做平行开发
2. Day 1 定义 AI 编码边界
3. 第一周做 3–5 个目标用户访谈
4. 阶段门禁写成脚本，不靠人工判定

**问：** "V7.1.1 Engine Core 化跨 4 个 Phase，你怎么保证每个 Phase 之间不引入回归？"

**答：** 每个 Phase 都重新跑上一 Phase 的全套回归；Phase 4 封箱前还专门加了 fuzz；Phase 6 做了跨 v714 / v721 双版本比对。Phase 4 → Phase 5 → Phase 6 这一链条就是"自我审计"的体现。

## 5. 复盘结论

- **项目统筹层面：** 阶段性封箱（每个 Phase 都独立验证）是这个项目能走完 12 个版本的关键
- **进度管控层面：** 三态分类（PASS / FAIL / PENDING）必须从 Day 1 就用，不能事后补救
- **需求规划层面：** "现象→根因→修复→验证"四段式让每个 bug 修复都可追溯
- **迭代优化层面：** 跨版本 Golden Master 比对是"对前面所有工作的最终验证"
