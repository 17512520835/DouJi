# 02 · 需求规划

> **本项目怎么决定"做什么 / 不做什么 / 什么时候做"。**
>
> 这一篇是 PM 能力的核心证据：我把模糊的"游戏 bug"和"用户反馈"翻译成可验证的需求项，再排进版本节奏里。

## 1. 需求来源分类

整个项目的需求来源只有三类，按优先级排列：

| 优先级 | 来源 | 示例 |
|--------|------|------|
| **P0** | 真实对局中暴露的阻断性 bug | V7.2.2 玩家选了"左前方移动"但实际向右前方结算 → 立刻修 |
| **P1** | 实测发现但未阻断的体验问题 | V7.2.3 手牌超过 8 张后无法点击查看详情 |
| **P2** | 架构性 / 长期投资 | V7.1.1 Engine Core Phase 1-4（确定核心封箱） |

**原则：永远不做没有真实对局场景支撑的"为做而做"的需求。** 这个原则在 27 篇迭代 MD 里都有迹可循——每一篇的"现象"段都是从具体操作序列出发的。

## 3. 关键需求项逐条解读

### 3.1 V7.1.1 Engine Core 化（Phase 1–4）

| 项 | 内容 |
|---|------|
| **为什么做** | 到 V7.0.x 时，单文件 HTML 已经超过 5MB，每次修改一个角色都要找很久；多人协作几乎不可能 |
| **目标** | 把"游戏规则核心"从 UI 里抽离，UI 只能通过 Observation 获取状态 |
| **成功标准** | Phase 4 封箱 6 条停止条件全部满足（见 `docs/05-架构契约.md` § 6） |
| **耗时** | 跨 4 个 phase、10+ 周 |
| **风险** | 旧代码迁移可能引入规则回归 → Phase 4 同时落地 `Observable Golden Master` 比对 |

### 3.2 V7.2.2 MovementDirection 一致性

| 项 | 内容 |
|---|------|
| **现象** | 玩家在 UI 选了"左前方"，但引擎结算到"右前方" |
| **根因** | 移动牌、技能移动、闪避反击各自有一套独立的"玩家意图 → 实际路径"解析，三套实现各自出现偏移 |
| **修复** | 统一收口到 `MovementResolver`，所有路径解析用同一份 Core legal action |
| **验证** | `v7.2.2_movement_direction_regression.js` + `V7.2.2_MovementDirection_验证报告.json` |
| **迭代文档** | `docs/iteration-archive/V7.2.2_MovementDirection_修复说明.md` |

### 3.3 V7.2.4 PassiveDraw SoftCap

| 项 | 内容 |
|---|------|
| **现象** | 长局（>20 回合）下，囚徒【抑制崩坏】和中央资源点的被动摸牌会把手牌顶到 12+ 张，玩家操作极其困难 |
| **根因** | 主动摸牌 / 被动摸牌共用同一个硬上限逻辑，没有区分 |
| **修复** | 5 张设为"软目标"而非硬上限——主动摸牌仍可超过，但被动摸牌遇到 5+ 张就停 |
| **为什么不一刀切硬封顶 5** | 那样会破坏既有策略（有的卡组刻意超 5 张配招），软目标保留策略空间 |
| **验证** | `v7.2.4_passive_draw_softcap_regression.js` + `V7.2.4_验证摘要.json` |

### 3.4 V7.2.10 战斗通报与囚徒回血修正

| 项 | 内容 |
|---|------|
| **现象（囚徒回血）** | 囚徒 013【抑制崩坏】在每大回合恢复 2 生命，比设计意图（"主动收势是较弱的奖励"）过强 |
| **现象（战斗通报）** | Online 联机界面缺少攻击 / 追击 / 技能 / 绝技的实时通报，玩家不知道对方在做什么 |
| **根因（回血）** | 数值参数沿用了 V7.0 时代"标准角色"的回血量，没有按"主动收势"的弱势奖励重新设计 |
| **根因（通报）** | Online 客户端只渲染自己手牌和当前回合信息，没接 Core 的 Event Ledger |
| **修复（回血）** | 改回 1，且明确"主动收势且本展开未攻击"为前提 |
| **修复（通报）** | Online UI 订阅 Core Event Ledger 中的攻击 / 追击 / 技能 / 绝技 / 展开推进事件 |
| **验证** | `V7.2.10_战斗通报与囚徒回血修正说明.md`（本轮轻量，不重跑全量回归） |

### 3.5 Online Phase 1（联机交付）

| 项 | 内容 |
|---|------|
| **为什么做** | 朋友间反馈"想远程对战但不想装客户端" |
| **目标** | 浏览器开链接即玩，2 人 P2P 房间 |
| **架构选型** | 权威服务器（Node.js HTTP + 自研 WebSocket）而非锁步模拟——因为隐藏信息（手牌 / 牌堆）必须服务端持有，不能下放客户端 |
| **不使用第三方方案的理由** | 不想引入 npm 依赖增加冷启动时间；想保持 0 依赖可独立部署 |
| **风险** | 服务器进程是状态常驻的，不能用 Serverless 部署 → 排除 Vercel / CloudStudio 这类 Maker 平台 |
| **解决方案** | 见 `docs/07-部署与发行.md` |

## 4. 我没放进来的需求（以及为什么）

| 拒绝的需求 | 拒绝理由 |
|----------|---------|
| 观战系统 | 联机刚上线，没人用得上观战 |
| 回放分享 | 单局没结束就被服务器重启覆盖，分享无意义 |
| 排行榜 / 积分 | 无持久化，无法做可靠排行 |
| 移动端原生 App | Web 版已覆盖手机浏览器，原生是 5 倍工作量且无明确收益 |
| 付费内容 | 项目性质是作品集，不商业化 |
| 多语言 | 中英文 UI 切换工作量大且不影响 PM 评估维度 |

## 5. 复盘：哪些决策我现在会改

- **V7.1.1 Engine Core 化 Phase 1–4 的耗时：** 当时低估了"老代码迁移"的工作量。下一项目我会先把"老代码冻结 + 新代码平行开发 + 逐步替换"作为第一阶段，而不是直接动老代码。
- **Online Phase 1 选择权威服务器而不是锁步模拟：** 锁步模拟能省服务器成本，但锁步模拟要求双方各自跑 Core、传输动作序。我们的 Core 已经 386KB，前端加载+首次同步会很慢。如果重新做，我会在 Phase 1 就尝试 lock步看实际延迟。
- **没有先做"用户访谈"：** 27 篇 MD 都是我自己测试对局 + 朋友小范围反馈。如果有真实用户样本，应该在 V7.0.2 之前就做一轮。
